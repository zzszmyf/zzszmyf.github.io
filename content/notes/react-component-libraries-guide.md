组件库选型最容易吵起来的问题是「Ant Design 还是 Material UI」，但真正决定返工量的，往往是产品里最难的那张表格。一个典型的中后台首页要服务端分页、列筛选、固定表头、行选择；Ant Design 的 Table 把筛选、排序、分页这些能力做在默认组件里，MUI 的高级 DataGrid 则放在 MUI X 包里，部分功能要付费。两边的差距最终会落到一笔账上：你愿意用工程时间换 license 预算，还是用 license 预算换工程时间。

把范围缩小到 React 生态，Ant Design 和 MUI 是两个默认起点，但它们背后的假设不同。AntD 来自阿里巴巴的中后台实践，设计取向是密集、务实，组件覆盖面广，表格、表单、树形、日期选择、上传这些高级能力开箱即用；代价是体积偏大，旧版依赖 moment.js，v5 之后换成了 dayjs，默认视觉也有很强的「Ant Design 味」，要大改需要投入。MUI 遵循 Material Design，移动优先，强调层级、阴影和卡片质感；它的基础组件扎实，复杂数据表格和日期选择器在 @mui/x-data-grid、@mui/x-date-pickers 里，部分能力付费；定制侧有 ThemeProvider、sx 属性和 styled API，摆脱原生 Material 样貌相对容易，tree-shaking 也做得更友好。MUI 更像一组小粒度组件，适合喜欢自己组合的团队；AntD 则偏向「电池全包」，把常用能力一次给齐。

选 AntD 的场景很具体：做管理后台、CRM、ERP、金融系统这类信息密度高的产品，工期紧，团队没有专职设计师，希望表格、表单、权限树这些能力开箱即用。选 MUI 的场景同样具体：面向消费者的产品、营销页、移动端体验重的应用，或者有品牌设计师参与、需要精细视觉定制和一套能扩展的设计系统。很多团队最后是混用的：C 端用 MUI，内部运营后台用 AntD。混用本身没问题，问题在边界：两套设计系统意味着两套间距、颜色和排版 token，两套主题机制，两套打包体积；如果共享组件跨过这条边界，维护成本会迅速超过「各用各的」省下的时间。

## Headless：自由和维修费一起买断

Headless 方案是另一条路。Radix UI 只提供无样式的行为和可访问性原语，样式完全自己写，很多现代 UI 库把它当基石；Headless UI 由 Tailwind Labs 出品，同样无样式，但更轻，和 Tailwind CSS 配合得最好；Shadcn UI 更极端，它把基于 Radix + Tailwind 的组件代码直接复制到你的仓库里，没有 npm 依赖，源码完全归你，近年在社区里很流行。这条路的好处是视觉和交互都能按产品改，不会被组件库的默认样式绑架；代价是升级不再由上游统一完成，可访问性、键盘导航、边界状态这些细节要自己接管。Shadcn 尤其像「买断」：你把代码拿走的那一刻，后续的 bug 修复和 API 变更也一起接手了。

## 设计感强的库：默认视觉能直接见人

设计感强的库解决的是另一类问题：默认视觉要能直接见人。Chakra UI 的风格现代简洁，Style Props 写法很顺手，比如 `color="blue.500"`，开发者体验好；但 v3 改动较大，社区出现分化，升级前要看清楚迁移成本。Mantine 的组件面非常宽，PDF 查看器、富文本编辑器、通知系统、日期时间都内置，文档和深色模式做得完整，开发体验接近 AntD，视觉更现代；代价是组件表面积大，打包和升级都要跟着它的节奏。HeroUI（原 NextUI）基于 Tailwind，视觉偏 Apple/Stripe 那种精致感，动效是卖点，适合追求设计感的 C 端产品；DaisyUI 则是 Tailwind 的组件化插件，用 `btn btn-primary` 这样的 className 就能拼出组件，极轻量，适合不想引入运行时组件库的页面。

## 大厂库：组织能力换生态规模

大厂出品的库往往在解决组织问题。Arco Design 由字节跳动推出，是 AntD 的直接竞争者，组件丰富、设计更现代，国际化和主题配置比 AntD 更灵活，字节内部大量使用；TDesign 由腾讯各团队联合出品，覆盖 Vue、React 和小程序，风格统一，企业级特性完善；Semi Design 来自抖音/今日头条，设计 tokens 系统成熟，支持主题实时切换，适合需要强主题定制的中后台。这些库的共同优势是背后有大规模业务验证和持续投入，共同风险是生态规模：文档、第三方组件、招聘市场的熟悉度通常不如 AntD/MUI，选之前要确认团队能不能接受更小的社区。

移动端是另一个分支。Ant Design Mobile 是 AntD 的移动版本，适合 hybrid App 或移动端中后台；Zarm 由有赞出品，移动端优先、组件轻量，适合电商类小程序/H5；React Native Paper 则面向原生 App，遵循 Material Design。移动端的选型标准和中后台不同：手势、滚动性能、安全区适配比表格能力更重要，别把桌面端的组件库直接缩到手机屏上。

## 选型的顺序

真正落地的顺序可以更细。先列出产品里最难的三类组件——通常是数据表格、日期范围选择器、富文本或文件上传——逐个确认候选库是内置、在扩展包里，还是要自己写；再确认主题机制能不能覆盖品牌色、圆角、间距和暗色模式；最后看打包和升级成本。AntD 的强项在表格、表单、树形这些中后台高频组件，MUI 的强项在移动端体验和主题系统，Headless 的强项在视觉自由度；把最难的三类组件对齐之后，选型基本就没有悬念了。项目生命周期也要算进去：长期维护看社区活跃度和版本稳定性，短期原型看开箱即用和文档完善度。

如果团队已经在用 Tailwind，Shadcn UI 的吸引力会明显上升：组件源码在仓库里，改样式不需要和上游的 CSS 优先级打架，也没有 npm 依赖带来的版本冲突；代价是组件的行为修复要自己跟，尤其是可访问性和边缘交互。反过来，如果团队没有前端基础设施、也没有设计师，AntD 或 Mantine 这种「组件 + 主题 + 文档」一体化的方案更稳，至少不用从零维护一套设计系统。

先定设计 token 和主题机制，再选组件库。组件可以逐个替换，token 一旦散进几百个页面就很难收回；顺序反了，第二次换库时会把同样的迁移成本再付一遍。
